Inheritance 
---------------------
    - mechanism where a class (subclass/childclass) acquires the properties and behavior of 
        another class (parentclass/superclass)
    
    why inheritance:
    - reusability (code reuse)
    - local hierarchy modeling
    - enalble runtime polymorphism
    - reduces duplication

    - inheritance represents IS-A relationship between super class and sub class 
    - in java, we use 'extends' keyword to inherit class 

        public class Child extends Parent {

        }

    - java supports "Single Inheritance" for classes 
    - Child class can :
        - inherit all non-private members (variables and methods)
        - override super class methods
        - additional members
    - constructors are not inherited, but the parent class constructor can be invoked 
        through "super()"   
    - by default, child class constructor always invoks superclass's no-arg constructor (if the super() is not used)

    Method Overriding 
    -----------------------
        - is an OOP feature in which a subclass provides its own implementation of a method already defined in the parent class, 
            using same method signature

        - Why override 
            - to implement polymorphism
            - to provide child specific behavior of the super class method 
            - to implement loose coupling 

        - How to override methods 
            - redefining a superclass method in the subclass with the same method signature 

        - Rules for method overriding 

            #1 - only inherited methods are overridden 
                    - default, public and protected methods of superclass can be overridden 
                    - private methods cannot be overridden 
            #2 - final and static methods cannot be overridden

            #3 - in subclass, the overridden method must have same method signature as per super class 

            #4 - the overriding method must have same return type or subtype 

                public class A {
                    public Shape show(){

                    }
                }

                public class B extends A {
                    public Rectangle shows() {

                    }
                }
            #5 - the overriding method must not have more restrictive access modifier 

                public class A {
                    protected void show(){

                    }
                }

                public class B extends A {
                    public/protected void shows() {

                    }
                }

            #6 - the overriding method must not throw new or broder exceptions 

                public class A {
                    public void show() throws Exception {

                    }
                }

                public class B extends A {
                    public void shows() throws Exception {

                    }
                }


    ***IMP : Overriding toString() method 
                - String toString() belongs to the java.lang.Object class 
                - it is used to return string representation of the object 

                - we can override the toString() method in anyclass to return a string 
                    representing some meaningful info of the object 
                    - printing object

                - if you DON'T override the toString()

    ***: Overriding the equals(Object obj) method
            - equals() is a method defined in java.lang.Object that is used to compare two objects for logical equality.

            public boolean equals(Object obj)

            - we can override the equals() method to define logic to compare two objects 

            - if we DON'T override 
                - the default Object.equals() is inherited 
                - by default, it compare the references of the given variables, not the contents 

            **equals() contract in java 
            -------------------------------
                - is a set of rules defined by java that every correct implemetation of equals method must follow 

                    Rule #1 - reflexive - An object must always be equal to itself.

                                x.equals(x) - should return true 

                    Rule #2 - Symmetric - Equality must work both ways.
                    
                        -  If x equals y, then y must equal x.

                         x.equals(y) == y.equals(x)

                    Rule #3 - Transitive - equality must be consistent 

                                x, y, z
                    
                    #Rule #4 - Consistent - equality should not randomly change 

                    Rule #5 - non-null references - no object is equal to null

    **What is hashCode 
        - hashCode() defined in the Object class, returns an integer hash value representing an object 
        - this hashCode value is primarily used in collections (set) to store/retrieve the elements efficiently 
        - **by default, the hashCode() method returns an integer value derived from the memory address of the object 

    **how set collections ensure uniqueness
        - first, it uses the hashCode() method, which returns an integer hash value, this value is used to find the "bucket index"
        - once the bucket index is calcualted, then it will check the bucket if there any similar object exists 
        - it uses the 'equals()' method to check equality  

    **for any Set based collections, you must override both hashCode() and equals() method 

    ** hashCode() and equals() contract 
        - hashCode() ---> decide "Where" to look (bucket)
        - equals() -----> decide whether the object are unique or not 

        - if two objects are exactly same, then their hashCode must also be same 
        - two unequal objects may have same hashCode

        ** Bean lifecycle 

                1. INSTANTIATION (Creating object)
                    - Spring reads bean definition (from @Component, @Bean, XML)
                    - Spring calls constructor (or factory method)
                        - by default no-arg constructor is called 
                        - Dependencies can be injected via constructor args at this point
                2. POPULATION (Dependency Injection)
                    - xml 
                        - dependencies can be injected using <property />
                    - java
                        - use the setter methods inside @Bean method logic 
                        - @Autowired setter methods are called (setter injection)
                        - @Autowired fields are set via "reflection" (field injection)
                    - Bean has all dependencies set now
                3. AWARE INTERFACES
                    - main purpose is to allow Beans to be aware of certain specific objects or environmental information within the Spring container. By implementing these interfaces, a Bean can obtain important resources from the Spring container during its initialization, such as the ApplicationContext 

                    - a java class can implement below interfaces 
                        - BeanNameAware 
                        - BeanFactoryAware 
                        - ApplicationContextAware

                    - BeanNameAware.setBeanName(String name) — bean receives its own name
                    - BeanFactoryAware.setBeanFactory(BeanFactory bf) — receives BeanFactory
                    - ApplicationContextAware.setApplicationContext(ctx) — receives context

                4. PRE-INITIALISATION (BeanPostProcessor)
                    - register the bean to the BeanPostProcessor 
                    - in this phase, the fields marked with @Autowired, @Value, @Resource will get processed 

                    - BeanPostProcessor.postProcessBeforeInitialization() — all registered BPPs called

                5. INITIALISATION
                    - the bean is fully constructed and dependeices are injected 
                    - during this phase, spring runs the intialization logic 

                    a. @PostConstruct method called (JSR-250 — Jakarta annotation)
                        - can be used to perform validation, to ensure the initialized values are correct 
                            - for example: db validation, validating the config, starting some background tasks 

                    OR
                    b. InitializingBean.afterPropertiesSet() called (if implemented)
                        - this older approach 

                    OR
                    c. Custom init-method called (if configured in XML or @Bean(initMethod=...))

                6. POST-INITIALISATION (BeanPostProcessor)
                    - BeanPostProcessor.postProcessAfterInitialization() — all BPPs called again
                    - THIS is where AOP proxies are created! (@Transactional, @Async etc.)

                    - manage the transactions, this the point to start the transaction 
                    - commit or rollback 

                7.  BEAN IS READY
                    - The bean is now fully initialized and available for use
                    - wrapped in proxy (if needed)
                    - managed by container 
                    - available to injection to the other object if needed 
                
                8. DESTRUCTION (on context shutdown)
                    - when Spring closes the ApplicationContext, all the beans are deleted 
                    - below methods can be used to close connections, flush caches, shut down thread pools etc.

                        a. @PreDestroy method called (JSR-250)
                            OR
                        b. DisposableBean.destroy() called (if implemented)
                            Or
                        c. Custom destroy-method called (if configured)

     -------------------------------------------------
        @OneToOne(
            fetch = FetchType.LAZY      //avoid auto-joining related entities 
            cascase = CascaseType.ALL   //persist / merge / remove will be automatically propogated
        )
        @JoinColumn(
            name = "FK_profile_id",
            nullable = false, 
            unique = true
        )

        **Owning Side 
            - controls the foreign key 
            - defines the @JoinColumn
            - Responsible for updating DB Relationship 

        **Inverse Side (mappedBy)
            - does NOT own the foreign key 
            - uses "mappedBy"
            - just reflects the relationship 


        **What is Fetch Policy 
        ----------------------------
            - defines how JPA loads "related entities"
            - with FetchType we can control whether the related entities should be loaded "Immediately (EAGER)" or "on-demand (LAZY)"

                    FetchType.EAGER --> related entities are loaded immediately along with parent entity 
                    FetchType.LAZY  --> related entities are loaded when accessed 

        **What is cascade 
        ----------------------
            - when you perform an operation on parent entity, the same operation is applied on the related entity automatically 
            - using CascadeType we can control propogation 

                    PERSIST     -> save parent ---> also save child 
                    MERGE       -> update parent ---> child also updated 
                    REMOVE      -> remore parent --> child also removed 
                    REFRESH     -> reload parent --> child also reloaded (retrieve)
                    DETACH      -> detaches entity from persistence context

    Spring Security
    -------------------------
        - provides authentication and authorization framework 

        <dependency>
			<groupId>org.springframework.boot</groupId>
			<artifactId>spring-boot-starter-security</artifactId>
		</dependency>

        **- after adding this dependeicy to the pom.xml, spring boot applies some auto-configuration,
             which by default enables "Basic Authentication"
            - by default, secures all the endpoints, it returns 401 Unauthorized 
            - by default, spring security protects every request 
            - it requires authentication unless you explicitely allow specific endpoints 

        **- "Basic Authentication"
            - By Default, spring security enables "Basic Authentication" which uses HTTP "Basic Auth"
            - a default user called "user" is created automatically with auto generated password 
                    - but you can define below properties in the application.properties file for a default user 

                            spring.security.user.name=vishal
                            spring.security.user.password=vishal123   

            - spring security also creates a default "login page" for authentication

            - by default, spring security enables "CSRF (Cross Site Request Forgery) " protection
                - the means, all the POST, PUT, PATCH, DELETE  endpoints are secured 

            - by default, spring security allows "Session based" security 
                - if you do not configure "Stateless mode", spring security can use HTTP session based authentication
                - the default behavior of Session Policy is 
                        SessionCreationPolicy.IF_REQUIRED
                - this means, spring may create a "Session" if needed, authentication can be stored in the session

            - by default, uses BasicAuthenticationFilter

    Microservices:
    -----------------------
        - it is an architectural style where the large application is broken into small / independently deployablable services 

        - Monolithic application
            - a single, unified codebase packaged and deployed as one unit 
            - simple to develop - one project, one ide, one run configuration
            - simple to test - integration tests cover the whole system in one shot 
            - simple to deploy - one artifact i.e. one .jar file, or one .war file. or one docker image 
            - simple to debug - all the logic, modules are written inside a single unit, one log file, one stack trace, one process 

        - Problems with Monolithic application
            - deployement coupling 
                - for every change, requires the entire application to be redeployed 

            - scaling inefficiency 
                - you can scale only the entire application, not any specific parts of the application 

            - technology lock-in 
                - use the same technology stack for the entire application 

            - team scaling conflicts 
                - merge conflicts 
                - coordination overhead 
                - slow build times 
            
            - fault propagation 


        - What makes the service "micro" 
            - single business Responsibility 
            - independently deployable 
            - owns its own data 
            - communcations via API 
            - Decentralized governance 
            - designed for failure
